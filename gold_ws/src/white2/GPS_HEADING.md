## 1. GPS 를 나누는 5단계

`gps.py` 가 GGA 의 `q` 를 그대로 쓰지 않고 다시 매긴다.

| 단계 | 이름 | 출처 | 실제 오차 | 판정 |
|---|---|---|---|---|
| **0** | ❌ `Q_NONE` | 무효 / NO_FIX | — | **발행 자체를 안 한다** |
| **1** | 🟡 `Q_SPS` | GGA q1 | 수 m | `status == 0` |
| **2** | 🟠 `Q_DGPS` | GGA q2 | ~1 m | `status == 1` |
| **3** | 🔵 `Q_FLOAT` | GGA q5 / q9 | 수십cm ~ 수m | `status >= 2` **and** σ > 0.30m |
| **4** | 🟢 `Q_FIXED` | GGA q4 | ~2 cm | `status >= 2` **and** σ <= 0.30m |

**아래 3단은 `status` 만으로, 위 2단은 σ 로만 갈린다.**

### 왜 위 2단에 σ 가 필요한가

드라이버(`nmea_navsat_driver`)의 매핑이 **Fixed 와 Float 을 같은 값으로 뭉갠다**:

```
GGA q=1 (SPS)       -> STATUS_FIX      (0)
GGA q=2 (DGPS)      -> STATUS_SBAS_FIX (1)
GGA q=4 (RTK Fixed) -> STATUS_GBAS_FIX (2)  ┐
GGA q=5 (RTK Float) -> STATUS_GBAS_FIX (2)  ├ ★셋 다 2★
GGA q=9 (WAAS)      -> STATUS_GBAS_FIX (2)  ┘
```

즉 `status >= 2` 는 "Fixed 이상"이 아니라 **"Float 이상"** 이다. 2cm 짜리와 수 m
짜리가 같은 숫자로 들어온다. 구별 정보는 같은 메시지의 `position_covariance` 에
이미 있어서, 그걸 σ 로 환산해 0.30m 로 자른다.

⚠️ **σ 를 모르면 Fixed 로 올리지 않는다.** σ=0 을 '아주 정확'으로 읽으면 최악의
입력을 최선으로 오해한다 — **모르면 낮게 본다.**

### 현재 문턱

`min_quality = Q_DGPS(2)` → **SPS 는 버리고 DGPS 이상은 받는다.**

```bash
ros2 param set /gps_node min_quality 4    # Fixed 만 쓰기
ros2 param set /gps_node min_quality 1    # SPS 까지 허용 (권장하지 않는다)
```

`1` 로 내리지 않는 이유 : `HeadingEstimator` 에 `기선 5m 도달 시 강제확정` 탈출구가
있어서, SPS(오차 수 m)면 그 경로로 **엉뚱한 헤딩이 박힌다.**

## 2. SPS 란 무엇인가

**SPS = Standard Positioning Service** — 수신기가 **보정정보 없이 위성 신호만으로
혼자 푼 해(解)**. GGA `q=1`.

★**SPS 는 "위성 신호가 약하다"가 아니라 "보정정보가 끊겼다"는 뜻이다.**★
위성은 그대로 잘 잡히는데 DGPS/RTK 보정 스트림이 안 들어오면 수신기는 혼자 풀
수밖에 없고, 그 순간 오차가 cm 급에서 **수 m 급으로 떨어진다.**

2026-08-19 로그가 정확히 그 모습이다. 대기 중 `DGPS ↔ SPS` 를 수십 번 왕복했는데
그 사이 **HDOP 는 0.5~1.0 으로 거의 안 변했다**(4절 계산). 위성 배치는 멀쩡했고
**보정 스트림만 끊겼다 붙었다 했다.**

| GGA `q` | 뜻 | 보정 출처 | 실제 오차 |
|---|---|---|---|
| 0 | 무효 / fix 없음 | — | — |
| **1** | **SPS (단독측위)** | **없음** | **수 m** |
| 2 | DGPS / SBAS | 코드위상 보정 | ~1 m |
| 4 | RTK **Fixed** | 반송파 + 정수모호성 **확정** | ~2 cm |
| 5 | RTK **Float** | 반송파, 모호성 **미확정** | 수십cm ~ 수m |
| 9 | WAAS | 광역 SBAS | ~3 m |

## 3. "RTK 보정 스트림이 달라졌다" 는 무슨 뜻인가

**원리** : 위치를 정확히 아는 **기준국**이 한 곳에 고정돼 있다. 기준국은 위성 신호로
자기 위치를 풀어 보고 *"정답을 아는데 지금 풀면 이만큼 틀리게 나온다"* 를 계속
방송한다. 차량 수신기가 그 오차를 자기 해에서 빼면 수 m → cm 급이 된다. 이 방송
데이터가 **RTCM**, 그게 흘러 들어오는 경로가 **보정 스트림**이다.

들어오는 길은 보통 둘이다 — **기지국 라디오 링크**(전용 무전기) 또는 **NTRIP**
(인터넷으로 상시관측소 서버에 접속).

### ★이 워크스페이스에는 보정 스트림을 다루는 코드가 아예 없다★

`nxde/README.md` 와 `launch/one_launch.py` 가 명시한다:

> `nmea_serial_driver` 는 수신기가 내보내는 NMEA 를 **읽을 뿐**이고 RTCM 보정을
> 넣지 않는다. 워크스페이스 전체에 NTRIP/RTCM 클라이언트가 없다. 즉 RTK 는
> **수신기 쪽 경로**로 들어와야 한다.

그래서 우리 코드는 보정에 **관여하지 않고**, 로그에는 결과(GGA `q`)만 드러난다.
그 결과가 이틀 사이에 이렇게 갈렸다:

| | GGA q | 우리 단계 | 뜻 |
|---|---|---|---|
| 08-18 20:11 | **4** 100% | RTK_FIXED | 보정 정상 수신, 정수해 확정 |
| **08-19 15:02** | **2 ↔ 1** | DGPS ↔ SPS | **q=4 가 한 번도 안 나왔다** |

즉 **"달라졌다"는 것은 코드가 아니라 코드 바깥의 보정 경로가 달라졌다는 뜻이다.**
RTK 보정이 아예 안 들어오거나, 들어오다 끊기다 하고 있다.

**확인할 순서 (전부 코드 밖이다)**

1. NTRIP 클라이언트를 따로 띄우는 구조라면 — 그게 **실행 중인지**, 접속이 살아 있는지
2. 인터넷 경유라면 — 네트워크/SIM 연결, 계정·마운트포인트
3. 라디오 링크라면 — 기지국 전원, 무전기 채널, 거리
4. 수신기 자체 설정이 초기화되진 않았는지 (RTK 모드, 보정 입력 포트)

## 4. `$GST` 란 무엇인가 — ★지금 안 나오고 있다★

먼저 용어 정리 — **DGPS 와 `$GST` 는 별개다.** DGPS 는 *측위 방식*이고 `$GST` 는
*수신기가 내보내는 NMEA 문장 하나*다.

**`$GST` = GNSS Pseudorange Error Statistics** — 수신기가 **"지금 내가 낸 해는
이만큼 틀릴 것 같다"** 는 자기 오차 추정치를 직접 실어 보내는 문장. 위도 방향 1σ,
경도 방향 1σ 등이 미터 단위로 들어 있다.

### 드라이버가 이걸 어떻게 쓰나

| `$GST` 가... | `position_covariance` 에 들어가는 값 |
|---|---|
| **나온다** | **수신기가 실시간 계산한 진짜 오차추정** |
| **안 나온다** | **q 별 고정 표 값 × HDOP** (SPS 4.0m / DGPS 0.1m / Fixed 0.02m) |

### 실측 — 안 나오고 있다

2026-08-19 로그의 원시표본 90개에서 σ 가 **딱 3개 값뿐**이다:

```
σ = 0.051m (43회) / 0.053m (1회) / 0.055m (46회)
  = HDOP 0.51 / 0.53 / 0.55  × 0.1m (DGPS 표 값)
```

SPS 구간도 같은 식으로 맞아떨어진다 — 이벤트 로그의 `σ=4.00m ↔ σ=0.10m` 쌍은
둘 다 HDOP 1.00 이고, 표 값 `4.0` 과 `0.1` 의 **40배 차이가 그대로** 나타난다.

### ★이것이 왜 중요한가★

코드는 σ 를 두 곳에서 **판정 기준**으로 쓴다(Fixed/Float 구별, 각종 문턱). 그런데
지금 σ 는 **수신기가 잰 값이 아니라 드라이버의 가정**이다. 특히 **DGPS 의 0.1m 표
값은 낙관적이다** — 코드 자신도 `Q_DGPS` 를 "오차 ~1m"로 적어 뒀다.

★**σ 0.055m 를 "5.5cm 정확도"로 읽으면 안 된다.**★

`$GST` 를 켜면(수신기 설정에서 NMEA-GST 출력 활성화 — u-blox 면 `UBX-CFG-MSG`)
σ 가 실제 값이 되고, σ 에 기대는 모든 문턱이 제대로 작동하기 시작한다.
**비용 대비 효과가 가장 큰 개선이다.**

## 5. 전체 로직 — 어떻게 돌아가는가

```
   /fix (5Hz)          /imu (자이로)      /encoder (펄스)
  nmea_serial_driver     iahrs.py          A보드
        │                   │                 │
        └───────┬───────────┴─────────────────┘
                ▼
         ┌──────────────── gps.py ────────────────┐
         │ ① 품질 판정   status + σ → 5단          │
         │ ② 이상치 게이트  물리(못 갈 거리) ·      │
         │                방향(옆걸음) · 품질      │
         │ ③ 앵커 갱신    NORMAL = fix 로 ★스냅★   │
         │ ④ 코스 갱신    연속 fix 변위 방위        │
         │ ⑤ DR 외삽     앵커 + ∫v·[cosψ,sinψ]dt  │
         │               ψ = 코스 + ∫자이로        │
         │               v = 엔코더(우선)          │
         └────────────────┬───────────────────────┘
                          ▼  /gps_fused (20Hz, 13개 배열)
         ┌──────────────── driving.py ────────────┐
         │ 위치 x,y  ← 그대로 사용 (DR 표본 포함)   │
         │ 헤딩      ← 초기확정 + ∫자이로 + 코스융합│
         │ 조향      ← CTE + 헤딩오차 → 펄스·각도   │
         └────────────────────────────────────────┘
```

**설계의 한 줄 요약** — 나가는 좌표는 언제나 `앵커 + 그 뒤 흐른 시간만큼의 추측항법`
이다. ★**상시 칼만필터가 아니다**★ — Fixed 일 때는 GPS 가 그냥 이긴다.

### IMU 가 두 곳에서 서로 다른 목적으로 쓰인다

| 어디서 | 무엇을 위해 | 절대 기준 |
|---|---|---|
| **gps.py** | **위치**의 빈 시간을 메우려고 (5Hz→20Hz) | GPS **코스**(변위 방위) |
| **driving.py** | **조향**을 계산할 차량 **헤딩** | `HeadingEstimator` 초기확정 |

★**둘은 독립이다.**★ gps.py 가 driving 의 헤딩을 받아 쓰면
`driving(헤딩) → gps(위치) → driving(헤딩)` 순환이 생기므로, 일부러 각자 자기
기준을 쓴다.

## 6. 헤딩을 잡는 방식 — 2단계

### 1단계 · 초기 확정 (`run_heading_init`)

DRIVE_HEADING 상태에서 **조향 0, 3펄스(≈9.5km/h)로 곧게** 굴리며 원시 fix 를 모은다.

- 헤딩 = **첫 점 → 마지막 점 벡터**
  (회귀를 안 쓰는 이유 : 등간격 N점 회귀의 방향오차는 두 끝점 방식의 √(6/N) 배라
  **N ≤ 6 이면 회귀가 오히려 나쁘다.** 표본은 대개 4~6점이다)
- 중간 점들은 **직진성 검사**(두 끝점 직선으로부터 수직거리 RMS)에만 쓴다
- 확정 조건 : `n >= 4` **and** `σ <= 3.0°` **and** `잔차 <= 0.15m`, 기선 `>= 1.0m`
- 탈출구 : 기선 `>= 5.0m` 면 정확도 미달이어도 **강제 확정**(⚠️ 로그에 남긴다)

**2026-08-19 실측** : `-14.76°`, σ **1.08°**, 잔차 **0.86cm**, 기선 **1.06m** →
**정상확정**(강제 아님). 어제 재생 분석의 예상(σ 1.0~1.2°)과 일치하고 잔차는 더 좋다.

### 2단계 · 주행 중 유지 — 자이로 적분 + 상보필터

```
매 IMU 샘플     : heading += gyro_z × dt                 ← 뼈대 (매끄럽지만 표류)
0.33m 갈 때마다 : heading += 0.05 × (course − heading)    ← 표류 억제 (★원시 fix 에서만★)
                  필요 변위 = max(FUSE_MIN_STEP_M 0.30m, FUSE_SIGMA_K 6.0 × σ)
```

**빠른 회전은 자이로가 즉각 따라가고, 느린 표류는 GPS 가 천천히 끌어당기는**
표준적인 상보필터 구조다.

★**원시 fix 에서만 융합한다**★ — DR 로 메운 표본을 먹이면 DR 톱니(메웠다가 다음
fix 에서 되돌아오는 움직임)가 **있지도 않은 방위 변화로 주입된다.**

**2026-08-19 실측** : 융합 **78회 / 36.2초**, 보정량 |corr| 중앙 0.044° 최대 0.856°
→ 역산한 코스-헤딩 편차 최대 **17.1°**(설계 목표 ~13°보다 약간 큼, 1회).

## 7. ★status 별로 헤딩 잡는 "방식"이 다른가 — 아니다★

**방식은 하나고, 다른 것은 문턱이다.** 다만 두 군데서 **다르게 작동하는 방법이
서로 다르다**:

| | 무엇이 status/σ 에 반응하나 | 성격 |
|---|---|---|
| **초기 확정** | `head_est.add()` 가 `fix_ok` 일 때만 불린다 | **on/off 스위치** (연속적이지 않다) |
| **주행 중 유지** | `need = max(0.30, 6σ)` | **σ 로 연속적으로 변한다** |

추정 알고리즘(끝점 벡터 + 직진성 잔차)과 확정 문턱(σ 3.0° / 잔차 0.15m)은
**품질별로 나뉘지 않는다.** `min_quality=2` 인 지금은 DGPS·Float·Fixed 가 **똑같은
방식으로** 들어가고, SPS 만 통째로 차단된다.

### σ 비례 문턱은 2026-08-19 주행에서 사실상 작동하지 않았다

원시표본 σ 중앙 **0.055m** → `need = max(0.30, 0.33) = 0.33m`.
설계 시 가정한 DGPS σ(0.14m → 0.84m)보다 훨씬 좋아서 **Fixed 대비 10%만 더 걸렸다.**
나쁜 뜻이 아니라 **걸릴 이유가 없었다**는 뜻이다. 단, 그 σ 가 표 값이라는 것이
4절의 문제다.

## 8. 주행 중 DGPS 보정 로직 — 실제로 도는 것은 3가지

먼저 오해를 하나 걷어내야 한다. 코드에는 `NORMAL ↔ DEGRADED` 라는 **모드 전환형
보정**(잔차 중앙값 융합)이 구현돼 있지만 **`DEGRADED_ENABLE = False` 로 꺼져 있다.**
2026-08-19 로그의 `gps_mode` 가 100% 0(NORMAL)인 것이 그 증거다.

그래서 **지금 품질이 낮을 때 실제로 도는 것은 모드 전환이 아니라, 항상 켜져 있는
이 3가지다** :

| # | 장치 | σ/status 를 어떻게 쓰나 | 08-19 결과 |
|---|---|---|---|
| 1 | **품질 게이트** | SPS(1) 이하 → `pos_ok=0` | 전 구간 통과 |
| 2 | **이상치 게이트** | 허용거리 = `v·Δt + ½a·Δt² + max(3.5σ, 0.12m)`<br>→ **σ 만큼만 관대해진다** | 기각 **0회** |
| 3 | **σ 비례 문턱** | 코스 갱신·헤딩 융합 모두 `max(고정값, 6σ)` | 0.33m (거의 무영향) |

여기에 품질과 무관하게 항상 도는 **DR 공백 메움**(5Hz fix → 20Hz 제어)이 깔려 있다.
08-19 실측 `dr_dist_m` 최대 0.726m, `raw_age` 최대 0.190s 로 정상 범위.

### ★핵심 : "덜 믿기"가 없다★

품질이 낮다고 **GPS 가중치를 낮추고 IMU 를 높이는 전환이 없다.** NORMAL 에서는
DGPS 든 Fixed 든 **fix 가 오면 그 좌표로 그냥 스냅한다**(블렌딩 없음).
낮은 품질에서 하는 일은 "덜 믿기"가 아니라
**"아예 버리기(게이트)" 또는 "판정 보류(문턱)"** 다.

### DEGRADED 를 꺼 둔 이유

DR 의 방향 기준을 **GPS 변위(코스)** 에서 얻는데, 비RTK 구간에서는 잡음이 한 샘플
이동보다 커서 ★**그 변위 안에 방향 정보가 없다**★. 문턱을 어디에 둬도 해결되지
않는다 — 게이트를 살리면(6.0) 코스가 낡아 융합이 무너지고, 코스를 살리면(2.0)
게이트가 나빠진다. 폐루프 시뮬에서 **최대오차가 +84% ~ −116% 로 케이스마다 갈렸고**,
추종 제어에서 중요한 것은 최대오차다.

```bash
# 켜 보려면 (로그의 gps_resid_m 을 확인할 것)
ros2 param set /gps_node degraded_enable true
```

## 10. 평가 — 괜찮은가

### ✅ 잘 돼 있는 것

- 초기 확정에 **직진성 검사 + σ 판정**이 있어 "안 곧게 갔는데 확정"을 막는다
- 상보필터 게인 0.05 는 **한 표본이 헤딩을 끌고 가지 못하게** 하는 적정값
- 융합·헤딩표본을 **원시 fix 에서만** 먹이는 것 — DR 톱니 주입 차단. 맞는 판단이다
- 게이트가 **σ 에 비례해 관대해지는** 것도 옳은 방향
- **실측이 증명한다** — 9절 표

### ⚠️ 우려되는 것 4가지

**① 자이로 바이어스 보정이 없다**
`driving.py` / `gps.py` / `iahrs.py` 전부 확인했고 **구현이 없다**(주석에서 문제로
언급만 한다). 코스 융합이 멈추는 구간(SPS 하락 · 저속 · 정지)에서는 헤딩이
**자이로 단독으로 표류한다.** 36초짜리 주행은 문제가 안 되지만 융합이 몇 초 이상
멈추면 각도로 쌓인다. 정지 중(엔코더 0)에 `gyro_z` 를 저역통과로 모아 빼는 방식이
표준이고, 구 `white/gps_imu.py` 가 하던 것이다.

**② σ 가 표 값이라 σ 비례 문턱이 낙관적이다**
4절 참고. `6σ` 로 보호하려던 것이 DGPS 에서 0.33m 밖에 안 걸렸다.
`$GST` 를 켜면 자동으로 해결된다.

**③ ★주행 중 품질 하락에 대한 방어가 없다★**
`fix_ok` 사용처가 3곳뿐인데 **전부 헤딩 관련이고 DRIVE_RUN 중 위치에는 안 걸린다.**
`cb_gps_fused` 가 `pos_ok` 를 보기 **전에** `self.x, self.y` 를 무조건 갱신하므로
**SPS(σ 3~4m) 좌표도 그대로 조향 계산에 들어간다.** 이때 달라지는 건 코스 융합이
멈춰 헤딩이 자이로 단독이 되는 것뿐이다. 08-19 주행 중엔 SPS 가 안 떴지만
**대기 중에는 수십 번 떴다** — 그게 주행 중으로 옮겨 오면 CTE 2.0m 경로이탈
안전정지에 걸려 **급정지**로 끝날 가능성이 크다.

**④ DEGRADED 융합이 꺼져 있고, 지금 구조로는 켤 수 없다**
8절 참고. 근본 원인은 **비RTK 구간에서 GPS 변위로 절대 방향을 얻으려는 것 자체**다.

### 종합 판정

현재 구조는 ★**"RTK Fixed 를 전제로 하고, 품질이 낮으면 판정을 포기하는" 설계**★다.
그 전제가 지켜지는 동안에는 잘 돌고, 08-19 DGPS 에서도 결과가 좋았다. 다만
**좋았던 이유는 보정 로직이 잘 대응해서가 아니라, DGPS 품질이 우연히 나쁘지 않았고
SPS 가 주행 중에 안 떴기 때문이다.** 방어가 실제로 시험받은 적은 아직 없다.
