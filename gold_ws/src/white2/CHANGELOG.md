  **주기 6~7 s** 로 12번 교차하고, 헤딩 std 2.7°, 요레이트 ±4~5 °/s, 지령 pot 이 −4 ~ 0° 를 느리게 오간다.
- 굽은 경로(A·C, 11~13 km/h, LFD 5~9 m)는 같은 성분이 ±0.2~0.3 m 로 작다.
- **조향 식별**(지령 → 요레이트, 4주행 모두) : 유효 백래시 반폭 **0.8~1.2° pot**, 1차 지연 0.15 s,
  순수지연 0.1~0.2 s, 전달비 1.50~1.85, 트림 −1.97 ~ −2.19°.

#### 2. 원인

**① 주원인 — 조향 서보 불감대가 백래시로 동작한다**

지령 경로 : driving 의 실수 pot → `arduino.py` 정수 반올림 → B보드 `atoi` → `updateSteer`
(`kasa_0909_B.ino`). |오차| ≤ 3카운트면 정지(0.5 s 뒤 SETTLED), 3~6카운트는 '죽은 영역' 정지,
**6카운트(1.78° pot)를 넘어야 PWM ≥ 110 으로 돈다.** 그래서 목표보다 ~1° 앞에서 서고, 방향이 바뀌면
그 1° 를 다 지나야 움직인다 = 백래시. 식별값 0.8~1.2° 가 그것이다.

순수추종의 횡강성(δ = 2L·e/Ld²)으로 이 유격을 옮기면:
```
e_유격 = (b / G) · Ld² / (2L)          b = 1.0° pot, G = 1.6, L = 1.25 m
  Ld  5.2 m (4펄스) → 0.12 m          ← 4펄스 때 안 보이던 이유
  Ld 11.2 m (7펄스) → 0.55 m          ← 163010 직선의 ±0.5 m 와 같다
  Ld 14.0 m         → 0.86 m
```
유격 안에서는 조향이 안 움직이는 채 흘러가다 끝에서 한꺼번에 꺾는다 → 한계순환이다.
**LFD 가 같으면 진폭은 속도와 무관하고 주기만 짧아진다 → 횡가속은 v² 로 커진다.**
(모의, 경로 B 직선 : 7 → 10펄스에서 CTE std 0.30 → 0.33 m 로 그대로, 요레이트 std 2.6 → 4.8 °/s,
횡가속 RMS 0.28 → 0.63 m/s², 주기 6.0 → 4.3 s)

**소거 실험**(경로 B 7펄스, 한 요인씩 없앰) — 백래시만 결정적이다:

| 없앤 것 | 직선 CTE std | 직선 요레이트 std |
|---|---|---|
| (현행 모델) | 0.30 m | 2.43 °/s |
| **백래시 1.0 → 0** | **0.15** | **0.84** |
| 정수 반올림 | 0.31 | 2.19 |
| 조향 지연 0.2 → 0 s | 0.23 | 1.93 |
| GPS 지연 · 자이로 잡음 · 트림 · CTE 적분 | 0.26 ~ 0.30 | 2.31 ~ 2.59 |

**② 코너 안쪽 파고듦 — 순수추종에 앞차축(안테나) 좌표를 넣고 있다**

순수추종은 **뒷차축** 기준으로 유도된 식이라, 뒷차축을 넣으면 원 위에서 정상상태 오차가 0 이다.
driving 은 GPS 안테나(앞차축 위) 좌표를 그대로 넣는데, 그 점의 속도는 헤딩이 아니라 헤딩 + δ 를
향하므로 원호가 접선이 되지 못해 **안쪽으로 붙는다.** 로그의 안쪽 편향 +0.19~+0.30 m 가 모의에서
+0.18~+0.23 m 로 재현되고, 뒷차축으로 옮겨 겨누면 −0.02~+0.01 m 가 된다.
(역모델 전달비 2.16 — 7펄스, 언더스티어 클램프 포함 — 대 실측 1.5~1.6 의 **과조향 1.35배**도 안쪽
편향에 보탠다. 단 이것만 고치면 아래 '기각' 표처럼 직선이 나빠진다.)

**③ 10펄스가 실제로는 9펄스다 — `LFD_MAX_M` 11.3 m**

`corner_speed` 의 (b2) ω_n 결속은 `lfd_win_only < lfd_speed` 이면 `v ≤ OMEGA_N_MAX·LFD/√2` 로 묶는다.
10펄스의 `lfd_speed` = 8.84·√2/0.78 = **16.0 m** > 상한 11.3 m → **직선에서도** v ≤ 0.95·11.3/√2 =
7.59 m/s = 8.6펄스 → **지령 9.** 모의에서 `drive_pulse:=10` 인데 지령 최대가 9 였다.
10펄스를 내려면 상한이 8.84·√2/0.95 = **13.2 m 이상**이어야 한다.

**④ 코너 속도가 `drive_pulse` 에 비례한다**

`demand_to_speed` 는 [drive_pulse, drive_pulse/2] 를 요구각 0~15° 로 선형보간한다. 같은 R 10 m 코너가
7펄스에서 4.5 m/s(**횡가속 2.0**), 10펄스에서 6.7 m/s(**4.5 m/s²**) 가 되고, 코너 하한도
int(10/2) = 5펄스(15.9 km/h)로 올라간다. 7펄스 로그의 횡가속 p99 는 0.5~1.1, 모의 10펄스 현행은 2.3~2.8
이다(자전거 모델이라 미끄러짐이 없는 **낙관값** — 실차는 더 나쁘다).

**⑤ 그래서 지금 코드로 10펄스를 올리면**(모의) — 흔들림 5.1~7.8 °/s(7펄스의 2~3배), 코너 최대
0.90~1.06 m. 차량 모델 오차 13종 중 **5종에서 경로이탈 안전정지(⛔ |CTE| > 2 m)** 가 난다(5절).

**⑥ 출발 직후 15 s 는 트림이 없다** — 트림 추정이 표본 300개(≈15 s) 뒤에 붙으므로(CLAUDE.md 4.1d,
사용자 결정 '주행마다 0 에서') 그 전에는 −2° 편향이 그대로 실린다. 아래 설계로도 10펄스의 최대 CTE
0.75~0.84 m 는 **출발 7초 뒤**에 난다(편향이 없으면 0.23~0.33 m).

#### 3. 설계 — 무엇을 어떻게 바꿨나 (★[2026-09-30] 구현됨 — 각 항목의 '→ 구현' 줄★)

**전부 파라미터이고 기본값은 '현행과 같음(끔)'** 이다 — 실차에서 하나씩 켜고 끄며 비교한다
(재빌드 없이 런치 인자로). 상수는 `driving.py` 상수절, 런치 인자는 `one_launch.py` (CLAUDE.md 7절 단일 소유자).

**A. 조향 백래시 선보상** — `steer_backlash_deg` (끔 = 0.0, 설계값 **0.8**) · `steer_backlash_hyst_deg` 0.3
→ **구현** : `driving._backlash_comp()` — `steer_command()` 의 두 반환 지점에서 `_with_trim()` 결과에 건다.
상태는 `reset_steer_shaping()` 이 지운다(`enter` · `_clear_transients` · `end_lidar_zone`).

`_with_trim()` 이 낸 **최종 pot(트림 포함)** 에 '움직이는 방향 × b' 를 더한다:
```python
# 상태 : self._bl_dir ∈ {−1, 0, +1}, self._bl_ext = 방향이 바뀐 뒤의 극값. enter() 에서 0 / None 으로.
u = out                                              # _with_trim 의 결과
if self._bl_ext is None: self._bl_ext = u
if   self._bl_dir >= 0 and u < self._bl_ext - h: self._bl_dir, self._bl_ext = -1, u
elif self._bl_dir <= 0 and u > self._bl_ext + h: self._bl_dir, self._bl_ext = +1, u
elif self._bl_dir > 0: self._bl_ext = max(self._bl_ext, u)
elif self._bl_dir < 0: self._bl_ext = min(self._bl_ext, u)
return clamp(u + b * self._bl_dir, ±STEER_MAX_DEG)
```
- 방향이 뒤집히는 순간 지령이 2b(정수로 2° = 6.75카운트) 튀어 **B보드의 6카운트 문턱을 곧장 넘긴다.**
- **driving 에만 둔다** — `arduino.py`(보드 규약의 소유자)에 두면 mppi·조이스틱까지 바뀐다.
- 모의 : 7펄스 흔들림 1.9~2.8 → **1.2~1.5 °/s**, 경로 B 직선 CTE std 0.30 → 0.15 m.
- ⚠️ **과보상** — 실제 백래시가 0 인데 0.8 을 주면(A~E 전체 기준) 불안정해지지는 않지만 지령 반전이
  58 → 154회/분, 서보 이동량이 2.4 → 6.2 pot°/s 로 는다(모터·드라이버 부담). **적용 뒤 새 로그를
  `follow_design.py log` 로 다시 식별해 b 를 맞춘다.** 설계값을 식별 범위(0.8~1.2)의 **아래쪽**에 둔
  이유다 — 덜 보상하는 쪽이 안전하다.
- 대안 **A′** — B보드 허용오차 축소(`../mad-code/kasa_0909_B.ino` `STEER_TOLERANCE_EXIT` 6 → 3~4,
  `ENTER` 3 → 2, `STEER_MIN_PWM` 재조정). 모의로 유효 백래시 0.5 는 A 와 비슷한 효과다. 목표 주위
  떨림(헌팅)을 벤치에서 먼저 봐야 하고 다른 저장소라, **A 로 모자랄 때** 검토한다.

**B. 순수추종 기하 = 뒷차축** — `pp_rear_axle` (끔 = false) · 새 상수 `GPS_ANT_X_M` (1.25 m — 안테나는 앞차축 위)
→ **구현** : `pure_pursuit_steer()` 의 기준점 `(ox, oy)` · 런치 `gps_ant_x_m`.

`pure_pursuit_steer()` 의 `to_body()`(그리고 그것을 쓰는 목표점 탐색)만 뒷차축 좌표로 한다:
```python
h = math.radians(self.heading)
rx = self.x - GPS_ANT_X_M * math.cos(h)            # 안테나 → 뒷차축
ry = self.y - GPS_ANT_X_M * math.sin(h)
# to_body(i) : dx, dy = wx - rx, wy - ry           (나머지 식은 그대로)
```
- **CTE·진행 포인터·종점 판정은 안테나 그대로 둔다** — 경로가 안테나 궤적이다. 그래서 `/lidar_ref[0]`
  도 그대로이고, B 를 켜도 mppi `handover.gps_antenna_x_m` 은 **그대로 둔다**(CLAUDE.md 7절의 'CTE 를
  뒤차축으로 투영하면 0 으로' 는 해당 없음 — CTE 는 투영하지 않는다).
- `GPS_ANT_X_M` = 뒷차축 → 안테나의 진행방향 거리 = **1.25 m** (안테나가 앞차축 위라 축거와 같다).
  0.35 m 어긋나도(모의 0.9 m) 코너 최대 0.38 m(같은 조건 현행 0.58 m) — 오차에 둔하다.
- 모의 : 7펄스 코너 최대 0.61~0.74 → **0.21~0.27 m**, 안쪽 편향 +0.18~+0.23 → **±0.02 m**.
- ⚠️ **단독으로 켜지 말 것** — 앞 안테나가 주던 선행(리드) 효과가 사라져 직선 흔들림이 다시 는다
  (경로 B : A 만 1.46 → A+B 1.86 °/s). **반드시 C 와 함께.**

**C. 요레이트 댐핑** — `yaw_damp_k` (끔 = 0.0, 설계값 **0.15** 도로휠° / (°/s))
→ **구현** : `apply_yaw_damp()`(`run_follow` 에서 순수추종 직후 · 적분 전) + `build_curve_profile()` 의 `wp_kappa`.
```python
# build_curve_profile() 에서 한 번 : self.wp_kappa[i] = 부호 있는 경로 곡률 (±3 m 창, + = 좌)
v = self.gps_ms()                                   # None 이면 댐핑을 끈다 (곡률 요구분을 못 뺀다)
r_ex = math.degrees(self.gyro_z - v * self.wp_kappa[self.wp_idx])   # 경로가 요구하지 않은 요레이트
self._yd += 0.3 * (r_ex - self._yd)                 # LPF (enter() 에서 0)
road += self.yaw_damp_k * self._yd                  # ★B보드 부호(+우)★ 왼쪽으로 더 돌면 오른쪽으로 민다
```
- 자이로 잡음 실측 1.8~2.0 °/s → LPF 뒤 ≈0.8 °/s × 0.15 = 도로휠 0.12° — 정수 지령(1° pot)보다 작다.
- 위치 : `pure_pursuit_steer()` 결과에, CTE 적분 전. 트림 추정(실측 pot ↔ 요레이트 회귀)과는 무관하다.
- 모의 : A+C 7펄스 흔들림 **1.09~1.25 °/s**(현행 1.89~2.82), 10펄스 1.22~2.25.

**D. 코너 속도 = 횡가속 상한** — `corner_ay_max` (끔 = 0.0, 설계값 **2.0 m/s²**)
→ **구현** : `corner_speed()` 의 (a2) 근거리 · (b) `v_corner` + `_ay_speed()` · `__init__` 의 코너 하한.
원거리 스캔은 런치 `curve_preview_far_m`(기본 24 = 종전 `CURVE_PREVIEW_FAR_MAX`).
```
v_corner(요구각) = √(corner_ay_max · R),   R = L / tan(요구 도로휠각)
근거리 : v_target = min(v_target, v_corner(near_for_speed))
원거리 : v_brake  = √(v_corner(far_for_gate)² + 2·BRAKE_GATE_DECEL·(gate − BRAKE_GATE_MARGIN))
         gate_v_corner 도 같은 v_corner 로 (corner_brake 가 그 속도를 겨누게)
코너 하한 펄스 : int(drive_pulse/2) 대신 3 에 고정 (10펄스에서 5 가 되지 않게)
CURVE_PREVIEW_FAR_MAX 24 → 40 m
```
- 원거리 40 m 근거 : 10펄스 → R 10 m 코너(4.47 m/s)를 1단(a 1.3)으로 맞추려면 (78.1 − 20.0)/2.6 × 1.2
  + 1.5 = 28 m, 보수 a 0.88 이면 41 m.
- 모의 : 10펄스 횡가속 p99 2.3~2.8 → **1.0~1.2 m/s²**(7펄스 로그 수준), 코너 최대 0.24~0.25 m.
  7펄스에서는 거의 걸리지 않는다(회귀 확인용).

**E. `LFD_MAX_M` 11.3 → 14.0 m** — ③ 때문이다. → **구현** : 런치 `lfd_max_m`(기본 11.3) —
`lookahead_m()` 다섯 곳 · `corner_speed()` 의 `cap_far` · LFD 초기값이 이 값을 쓴다. 7펄스(11.22 m)는 그대로, 8펄스 12.8 m, 9·10펄스 14 m
(10펄스 실효 ω_n 0.89, 식별 지연 0.35 s 로 위상여유 ≈ 47°).
- ⚠️ 유격 ∝ Ld² — **A·C 없이 E 만 하면** 유격 0.55 → 0.86 m. 반드시 A·C 다음에.
- ⚠️ 라이다 복귀 재수렴(CLAUDE.md 4.1b-2)의 잔류 CTE 도 Ld² 로 커진다(14 m 에서 ≈1.9 m, 문턱 0.5 m).
  **L 구간이 있는 경로는 그쪽 ②(재수렴 구간만 2펄스 기준 LFD)를 먼저 한다.**
- CLAUDE.md 7절 짝 : `LFD_MAX_M` ↔ `LFD_OMEGA_N_FAST` ↔ `one_launch.py` `lfd_*` ↔ `OMEGA_N_MAX`(b2).

**F. (결정 필요) 출발 직후 트림 없음(⑥)** — ① 하드웨어 영점 캘리브(`BOARD_B.md` 3절 `a`)가 근본이고,
② 직전 주행 트림을 초기값으로 쓰기(4.1d 의 사용자 결정 '주행마다 0' 을 바꾸는 일), ③ 트림이 붙기 전

## 2026-09-01 — ★GPS 추종과 라이다 회피를 한 주행 계통으로 합쳤다★

> (`lidar/README.md` 6절 '남은 결정' 에 그 질문이 남아 있었다). 이제 한 경로 안에서

### ① 어떻게 지정하나 — 매핑 CSV 의 미사용 열 `terrain`

`mapping.py` 는 이 열에 늘 `"0"` 을 쓰고 **읽는 코드가 어디에도 없었다**(경로 로더는
`latitude`·`longitude` 만 읽는다). 그 빈 칸을 그대로 쓴다:

    terrain 이 'L' 또는 'l'  → 라이다(mppi)가 몬다
    그 밖의 모든 값          → GPS 추종(driving)이 몬다

`0` · 빈 칸 · **열 자체가 없는 CSV** 도 전부 GPS 로 떨어진다 — 즉 **기존 CSV 6개가
그대로 돌고**, 매핑 코드는 한 줄도 바뀌지 않았다. 사람이 매핑한 뒤 CSV 를 열어

### ② 왜 '허락' 인가 — 발행자를 시간축에서 배타로 만든다

`/cmd_vel_raw` 는 마지막 발행자가 이기는 토픽이고, `nxde/arduino.py` 의 `cb_cmd_vel`
은 **신선도를 보지 않고 마지막 펄스를 래치한다.** 그래서 두 노드가 동시에 내면 20Hz
로 서로를 덮고, 한쪽이 조용히 죽으면 차가 **직전 펄스로 계속 굴러간다.** 겹치지
않게 하는 것이 이 설계의 전부다.

    driving ──/lidar_permit(Bool)──▶ mppi     "이 구간은 네가 몰아라"
    driving ◀──/lidar_active(Bool)── mppi     "나 살아 있다" (매 틱)

    G 구간 : driving 이 발행  ·  permit=False → mppi ★침묵★
    L 구간 : driving ★침묵★   ·  permit=True  → mppi 가 발행

`/tl_permit`(신호등 개입 허락)과 **같은 규약**이다 — 값을 매 틱 계속 내므로
**신선도가 곧 허락**이고, 발행자가 죽으면 값이 끊겨 상대가 스스로 손을 뗀다.

`/lidar_active` 가 없으면 이 기능은 성립하지 않는다. 허락을 일방적으로 내보내는
설계로는 **mppi 가 안 떠 있는 상태**(`use_lidar:=false` 로 L 구간 CSV 를 주행)를
알 방법이 없고, 그때 driving 이 침묵하면 아무도 몰지 않는 채로 차가 달린다.
지금은 그 경우 이양하지 않고 **그 자리에서 정지 + 리니어 2단**이다.

### ③ ★mppi 는 L 구간마다 기준선을 다시 잡아야 했다★

이것이 이 작업에서 실제로 위험했던 곳이다. `mppi_local_planner_node` 의
`heading_ref_yaw_` 는 **런치 직후 자이로 보정 단계에서 딱 한 번** 잡히고 그 뒤로는

기본 보존이다. `one_launch` 로 white1 과 함께 띄우면 그 값은 **출발 주차 위치의
방위**이고, 수백 미터 뒤 L 구간에서 그 노드는 **그 선으로 복귀하려 한다.**

목표펄스 | 최대 4 | **최대 2** (큰 CTE 를 4펄스로 파고들면 경로를 가로지른다) |

시한 | — | **12 s** (못 붙으면 정지 — 유예를 무한정 열지 않는다) |

조향은 평소와 같은 순수추종이다. 목표점이 경로 위에 있으므로 그것만으로 수렴한다.
`|CTE| ≤ 0.5m` 이 되면 평소 규칙으로 돌아간다.

**`wp_idx` 는 다시 잡지 않는다.** L 구간 동안에도 `advance_wp_idx()` 를 계속 부르므로
(발행만 멈췄고 노드는 계속 돈다) 포인터는 이미 실제 위치를 따라와 있다. 그 함수는
위치 기반 최근접이라 mppi 가 횡으로 2~3m 벗어난 채 지나가도 따라 올라간다.
`align_start_wp()` 처럼 전역 최근접을 다시 찾으면 순환 코스에서 반대편 구간으로
건너뛸 수 있다.

### ⑤ 두 발행자가 겹칠 수 있던 나머지 창을 막았다

- **`loop()` 의 E-STOP·GPS두절 분기** — 이 둘은 `run_follow()` 에 닿기 전에 스스로
  `send(0)` 을 낸다. L 구간 중에 발동하면 두 발행자가 동시에 **다른 값**(mppi 2펄스 /
  이쪽 0)을 내는 유일한 창이 열린다. → `_revoke_lidar()` 로 발행 재개 **전에** 허락을
  내린다. 사정이 풀리면 `begin_lidar_zone()` 으로 새로 이양한다(그때 mppi 가 기준선을
  다시 잡으므로, 서 있던 동안 낡아진 추측항법을 들고 재개하지 않는다).
- **리니어 소유권** — mppi 가 구간 끝에서 장애물을 보고 2단을 물고 있으면
  `/brake_level` 의 마지막 값이 2 인 채로 남는다. driving 의 `brake_now` 는 0 이지만
  `_publish_brake` 는 **'0 은 재확인하지 않는다'** 는 규칙 때문에 스스로 풀지 않는다
  → **브레이크를 물고 달린다.** 양쪽에서 막았다: mppi 는 하강엣지에서
  `releaseBrake()`, driving 은 `end_lidar_zone()` 에서 0 을 **한 번** 강제 발행한다
  (주기적 재확인이 아니라 이양 경계에서 한 번이므로 그 규칙과 충돌하지 않는다).
- **`enter()`** 가 상태 전이마다 이양·재수렴을 내린다. 도착해 선 차를 mppi 가 계속
  모는 일이 없다.

## 2026-08-21 — B보드 제동등·A5 텔레메트리 · ★E-STOP 을 '일시정지'로★

> 실차 로그가 아니라 **지시사항에 따른 설계 변경**이다. 세 갈래이고 서로 얽혀 있다 —
> ①펌웨어가 값을 하나 더 보내기 시작했고 ②E-STOP 의 의미가 바뀌었으며 ③그에 맞춰
> 안내음성 규칙이 바뀌었다. 보드 쪽 계약은 `BOARD_B.md` 에 따로 정리했다.

### ① 펌웨어 — `kasa_0821_B.ino` (`kasa_0813_B.ino` 기반, 제어 로직 무변경)

**제동등(D11)** 을 추가했다. 12V 램프를 모터드라이버로 켜되 IN1=HIGH / IN2=LOW 는
배선에서 고정하고 아두이노는 PWM 선만 `digitalWrite` 로 잡는다(세기 조절 없음 →
타이머를 안 쓰므로 조향 D7·리니어 D9 PWM 과 간섭 없다).

    A5 ≥ 400 → 점등   (소등 392 미만, 히스테리시스 8)

**판정에 쓰는 것은 A5 하나뿐이다** — `brake_level` 도 `auto_mode` 도 `estop` 도 보지
않는다. 조건이 '차가 무엇을 지시받았는가'가 아니라 **'페달이 실제로 내려갔는가'**
이기 때문이다. 자율주행이 리니어로 밟든 사람이 발로 밟든 E-STOP 이 밟든 뒤차에게는
같은 사건이다. `loop()` 맨 앞에 있고 어떤 분기에도 들어가 있지 않아 E-STOP 중에도
캘리브레이션 중에도 수동조종에서도 동작한다.

이를 위해 **A5 샘플링을 살려야 했다.** 0813 은 리니어를 움직이는 동안과 1·2단 처짐
확인 때만 A5 를 읽었고 **0단 대기 중에는 아예 읽지 않았다** — 즉 사람이 발로 밟은
것을 볼 수 없었다. 제동등이 가장 필요한 경우가 그것이다(`refreshLinPot()`, 20ms).

출력 양식이 한 필드 늘었다: `P,<조향각>,<모드>` → **`P,<조향각>,<A5원본>,<모드>`**.
A5 는 단계가 아니라 **환산 없는 raw** 다 — 단계로 바꾸면 '사람이 발로 밟았다'가
사라지고, 그것이 수동조종 구간에서 유일하게 움직이는 값이다.

### ② `/estop` 이 '주행 취소' → **'일시정지'**

종전([2026-08-14])에는 E-STOP 이 걸리면 진행 중이던 자율주행을 **버리고** IDLE 로
돌아갔다. 실차에서는 그것이 매번 '메뉴로 가서 경로를 다시 고르고 헤딩을 다시 잡는'
절차였다 — E-STOP 은 시험 중 자주 눌리는데 한 번 누를 때마다 주행 한 판을 버렸다.

| 상황 | 종전 | 지금 |
|---|---|---|
| `DRIVE_HEADING`/`DRIVE_RUN` 중 체결 | `enter(IDLE)` — 경로·헤딩 폐기 | **상태·WP 인덱스·헤딩 유지, 제자리 정지** |
| 해제 | (없음 — 사람이 다시 시작) | **1.5초 뒤 그 자리에서 재개** |
| `MAP_*` / `DRIVE_DONE` 중 체결 | 무변화 / 취소 | **둘 다 무변화** |
| 시작 전 체결 | `DRIVE_START` 만 거절 | **`MAP_START` 도 거절** (화면이 대기) |

- 붙잡는 곳은 `driving.loop()` 의 게이트 한 곳이다(펄스 0·조향 0 을 내고 `return`).
  GPS 두절 판정보다 **앞에** 둔다 — 서 있는 동안 할 말은 하나뿐이라 경고가 겹치면
  원인이 흐려진다.
- 체결 시 `_estop_pause_reset()` 이 **과도 상태만** 지운다 — 종점 접근 단계, 코너 1단
  제동, CTE 적분, 리니어. 이것들은 *"지금 v 로 굴러가고 목표까지 d 남았다"* 는 전제
  위에 서 있어서, 서 있는 동안 그 전제가 통째로 무효가 된다. 들고 있다가 재개하면
  낡은 전제로 판단한다. **상태·WP·헤딩은 건드리지 않는다** — 그것이 이 변경의 요점이다.
- 일시정지 중에는 헤딩 추정기에 GPS 표본을 넣지 않는다(`head_est.add` 게이트). 서 있는
  차의 드리프트가 직선 밖에 점을 뿌리면 직진성 검사(resid)가 나빠져 확정이 늦어진다.
- **매핑도 E-STOP 이 풀려야 시작한다** (종전엔 매핑만 예외였다). 화면의 대기 절차를
  ①스위치 → ②E-STOP 두 단으로 통일하기 위함이고, 매핑 **도중** 체결은 종전대로
  아무 상태도 바꾸지 않는다.

> ### ⚠️ 트레이드오프 — 해제가 곧 출발이다
> 사람이 차 옆에서 E-STOP 을 되돌리는 순간 차가 **스스로** 움직이기 시작한다. 종전
> 코드가 명시적으로 피하려던 상황이다. 그래서 해제 즉시가 아니라
> `ESTOP_RESUME_GRACE_S`(**1.5초**) 만큼 펄스 0 으로 붙잡는다. 근거 두 가지 —
> 사람이 손을 뗄 시간, 그리고 **B보드가 리니어를 0단으로 되돌리는 1000ms**
> (`BRAKE_HOME_MS`). 그 전에 구동을 걸면 브레이크가 아직 빠지는 중인 채로 민다.
> 첫 실차 시험은 사람이 차에서 떨어진 상태로 할 것.

### ③ 시작 대기가 **2단 게이트** 로 — `prompt.py`

1)매핑·2)주행 을 누르면 **①스위치 → ②E-STOP** 순서로 확인하고, 어긋난 단계에서
기다린다. 둘 다 맞는 순간 START 가 나간다. **순서가 곧 안내 우선순위다** — 둘 다
어긋나 있으면 스위치 안내만 먼저 나가고, 스위치를 넘기면 그때 E-STOP 안내가 나간다.
대기 중 스위치가 다시 어긋나면 ①로 되돌아가고 안내도 다시 나간다.

E-STOP 으로 **대기를 취소하지 않는다.** 종전에는 주행 대기 중 E-STOP 이 걸리면 대기를
접고 메뉴로 돌려보냈는데(그때는 `driving` 이 거절했으니 맞는 처리였다), 이제는
'거절'이 아니라 '한 단계 더 기다림'이다 — 눌러 둔 사람의 의도를 버리지 않는다.
메뉴의 "E-STOP 중 주행 시작 불가" 거절도 없앴다.

2단은 실측 2.2~3.8 m/s² 라 4펄스(3.54 m/s)를 **1.1초 만에** 1.11 m/s 로 떨어뜨린다.
그 뒤 남은 2.4m 를 1펄스로 기어가고, 도착에서 다시 2단으로 선다. **세 박자다.**

### 무엇을 바꿨나 — 속도로 계산한 지점에서 1단

```
종전 : 종점 5m 고정 → 2단 → 4km/h 에서 해제 → 1펄스 크립 → 도착 2단
지금 : need₁ = v·t_lag + v²/(2·a1) + margin  지점에서 → ★1단★
       → (미달이면) 크립 → 도착 즉시 ★2단★ → 완전정지 → 주행 종료
```

| 진입 속도 | 1단 체결 지점 `need₁` | (참고) 2단 백스톱 문턱 |
|---|---|---|
| 4펄스 3.54 m/s | **15.8 m** | 5.2 m |
| 3펄스 2.65 m/s | 9.4 m | 3.2 m |
| 2펄스 1.77 m/s | 4.8 m | 2.0 m |

- `t_lag = 0.55s` : GPS 속도창 중심 0.20 + 시리얼 0.05 + 리니어 1단 행정 0.54 의
  **유효분** 0.30(행정 중 제동력이 0→a1 로 올라오므로 앞 절반은 사실상 제동이 아니다).
- **감시 창(`goal_brake_m`) 기본값을 5.0 → 20.0 으로 올렸다.** need₁ 이 15.8m 라
  5m 창으로는 '이미 늦은 지점'에서만 물게 된다. `5.0` 을 주면 사실상 종전 거동이다.

### `a1 = 0.47` — 왜 코너 제동의 `A_BRAKE1_MS2(0.88)` 와 다른 값인가

**쓰이는 방향이 반대라서 일부러 따로 뒀다.**

| | 코너 제동 | **종점 제동** |
|---|---|---|
| a 를 크게 잡으면 | 늦게 물어 **코너를 넘는다**(위험) | 늦게 물어 **종점을 지난다**(위험) |
| a 를 작게 잡으면 | 일찍 물어 느려질 뿐(안전) | 일찍 서고 **크립이 메운다**(안전) |
| 그래서 쓰는 값 | 보수적 **하한** 0.88 | **최저 실측** 0.47 |

0.47 은 2026-08-18 실차의 **구동차단 1단** 실측이다. BRAKING.md 1절의 0.62~1.05 는
*지령펄스가 살아 있던* 값이라 직접 비교가 안 된다 — 즉 참값은 **0.47~1.05 사이**이고,
그 폭을 ① 낮은 쪽으로 계획하고 ② 그보다 약하면 백스톱이 받는 방식으로 처리한다.

### 2단 백스톱 — 종점 통과를 막는 마지막 방벽

제동 중 매 틱 "**지금 2단으로 세우려면 몇 m 가 필요한가**"(`need₂`, 안전계수 1.2)를
함께 계산하고, 남은 거리가 거기 닿으면 2단으로 올린다. 4펄스에서 **5.2m** 라
**2026-08-12 의 5m 2단 접근제동이 필요할 때만 자동으로 되살아나는 것**과 같다.
올리기만 하고(1→2) 내려오지 않는다. 이미 크립 속도 밑이면 올리지 않는다(그 속도의
2단 정지거리는 0.28m 다).

### 폐루프 시뮬로 잡은 결함 1건 (수정함)

**창 안으로 이미 늦게 진입하면 1단과 2단을 같은 틱에 물었다.** B보드는 진행 중인

### 미달이면 크립 — 다만 ★가능하면 서기 전에 넘긴다★

## 2026-08-18 (3) — GPS 이상치 게이트 (+ DEGRADED 융합은 만들었으나 ★끄고 둔다★)

같은 날 (1) 에서 만든 `gps.py` 에 **"말이 안 되는 값은 버린다"** 를 넣었다. 함께
요청받은 **비RTK 지속 구간의 DR+평균 융합**도 구현했지만 **폐루프 시뮬에서 결과가
케이스마다 갈려 기본 OFF 로 둔다** — 이유는 아래 '왜 껐나'.

### 무엇을 넣었나 — 게이트 세 겹

| | 무엇을 보는가 | 근거 |
|---|---|---|
| **물리** | `허용 = v·Δt + ½a·Δt² + max(바닥, 3.5σ√2)` 를 넘는 점프 | 이 차는 0.2초에 5m 를 못 간다 |
| **방향** | 변위 방위가 진행축과 거의 90°(옆걸음) | 자동차는 옆으로 못 간다 |
| **품질** | `Q_NONE` → 애초에 발행하지 않음 | (1) 에서 이미 넣음 |

**σ 를 허용량에 넣는 것이 핵심이다.** Fixed(σ 0.02)에서는 게이트가 타이트하고
Float(σ 2~4)에서는 느슨해진다 — **수신기가 스스로 밝힌 불확실성만큼만 관대해진다**
(통계 용어로 innovation gating). 캡(5.0m)이 없으면 Float 에서 17m 까지 열려 무력해진다.

**★탈출구가 반드시 있어야 한다★** RTK 가 재수렴하면 **진짜 위치가 몇 m 점프한다**
(직전 해가 틀렸던 것이다). 게이트만 있으면 그 옳은 값을 영원히 거부하고 낡은 DR 로
달린다 — **게이트가 없는 것보다 더 위험하다.** 연속 5회(=1초, driving 의 두절
타임아웃 2초보다 짧다) 기각하면 받아들이고 코스·속도·잔차 이력을 버린다.
※ 첫 구현에서 이 탈출구가 **상수만 있고 판정에 안 들어가 있었다**(로그 문자열에만
쓰였다). 시뮬로 잡았다.

### ★시뮬레이션이 잡은 결함 4건★ (전부 수정)

1. **잡음을 한 번만 셌다** — 게이트가 보는 것은 *두 fix 사이의 거리*이고 거기엔 양쪽
   잡음이 다 들어간다(독립이므로 σ√2). 빼먹으니 σ=1 구간의 fix 를 **절반(28/58)
   기각**했고, 데이터가 굶어 융합이 **-81%** 악화됐다.
2. **3σ 로 잘랐다** — '3σ=99.7%' 는 정규분포 이야기다. 2D 벡터 차의 크기 상한은
   균일 잡음에서 **4.9σ** 다. 3σ 면 정상 꼬리를 버려 **최대오차가 -77% 악화**됐다.
   → `GATE_SIGMA_K` 3.0 → **3.5**(×√2 = 4.95σ).
3. **방향 게이트가 잡음 구간에서 정상 fix 를 기각** — σ=0.5 에서 한 샘플 이동은
   0.4m 인데 잡음차는 ±2m 다. 즉 **측정된 방위가 난수**인데 '60° 이상'으로 판정하니
   난수의 1/3 이 걸렸다. 기각된 표본들의 jump 가 1.5~2.6m(이동 0.4m)로 숫자에 드러났다.
   → 문턱을 σ 비례로(`DIR_SIGMA_K = 6.0`) = **방향 게이트는 사실상 Fixed 전용**이 된다.
   **'잡음이 크면 방위 판정을 포기한다'가 맞는 답이다.**
4. **자이로 누적을 fix 마다 리셋했다** — `psi = 코스 + 자이로적분` 인데 그 적분을
   앵커 갱신(=매 fix)마다 0 으로 되돌렸다. NORMAL(0.2초)에서는 차이가 없지만, 품질이
   나빠 코스가 몇 초간 갱신되지 않으면 **그 사이 돈 각도가 통째로 사라져** DR 이
   '몇 초 전 방향'으로 직진한다. → 리셋은 **코스가 갱신될 때만**(`_yaw_ref`).

### 사용자 지적 반영 — 출발 직진 구간에서 첫 방위를 잘 잡는다

주행은 **출발 직후 조향 0 으로 곧게 굴러가는 구간**에서 시작하고, 그때 잡은 코스가
이후 DR 방향의 **절대 기준**이 된다. 기선 길이가 그대로 정확도가 된다:

```
0.30m → atan(0.028/0.30) = 5.4°        1.00m → 1.6°
```

→ **첫 코스만 1.0m 기선을 요구**한다(`COURSE_FIRST_MIN_STEP_M`). 이후 갱신은 0.30m 로
짧게 — 코너에서 방위를 따라가야 하기 때문이다. driving 의 `HEAD_MIN_DIST_M` 도 같은
이유로 1.0m 라 두 값을 맞췄다. 확정 시 로그를 남긴다(`🧭 GPS 코스 확정 …`).

### 검증 — ★폐루프 시뮬레이션. 실차 아님★

실제 `cb_fix`/`_gate`/`_advance_dr` 등을 그대로 호출하고, 20Hz 발행 틱까지 돌려
**발행 좌표(앵커+DR)** 를 참값과 비교했다. 1200표본 × 3시드:

| 시나리오 | 평균 | p95 | **최대** | 기각 |
|---|---|---|---|---|
| Fixed σ=0.02 정상주행 | 0.154→0.019 (+88%) | +89% | 0.320→0.052 (**+84%**) | 0 |
| 백색 σ=0.5 | +2% | +7% | 1.325→1.164 (+12%) | 0 |
| 백색 σ=1.0 | +0% | +1% | +3% | 0 |
| 상관편향 τ=3s (실제 Float 성질) | +11% | +13% | 1.071→0.925 (+14%) | 0 |
| 상관편향 τ=8s | +3% | +6% | +0% | 0 |

**악화 0건.** 정상주행(+84%)의 개선은 게이트가 아니라 **(1) 의 DR 공백 메움**이 낸
것이다 — 5Hz fix 사이 3틱이 낡은 좌표를 쓰던 것이 사라졌다.
**단발 튐(+82%)이 이번 변경의 목적이고 그대로 달성됐다.**

### 왜 DEGRADED 융합을 껐나 — ★구조적 한계를 시뮬이 드러냈다★

구현 자체는 의도대로 동작한다. **좌표를 직접 평균하지 않고 잔차(= fix − DR예측)의
중앙값을 따라간다** — 차가 3.5 m/s 로 달리는 중에 1초치 좌표를 평균하면 3.5m 뒤처진
점이 나오므로, DR 로 운동을 먼저 빼야 '순수 위치오차'가 남는다. 사용자가 말한
"IMU 방향이 있으니 GPS 위치를 찍기 편하다"가 이 구조다. 평균이 아니라 **중앙값**인
이유는 막으려는 것이 '한두 표본의 큰 튐'이기 때문이다.
(구현 중 **창 rebase 누락**도 시뮬로 잡았다 — 보정 후 창의 잔차가 낡은 기준을 물고
있어 이중 계산이 되어 수렴하지 않았다.)

**그런데 최대오차가 케이스마다 +84% ~ −116% 로 갈린다.** 상관 편향(실제 비RTK 성질)
에서는 평균 +24~36%/p95 +15~21% 로 좋지만, 백색 잡음과 선회에서 최대가 무너진다.
추종 제어에서 중요한 것은 **최대오차**다 — 그것이 CTE 스파이크와 조향 급변을 만든다.

**원인은 방향의 출처다.** DR 의 절대 방향을 **GPS 변위(코스)** 에서 얻는데, 비RTK
구간에서는 잡음이 한 샘플 이동보다 커서 **그 변위 안에 방향 정보가 없다.** 문턱을
어디에 두든 해결되지 않는다는 것이 숫자로 나왔다:

| `COURSE_SIGMA_K` | 게이트 최대오차 | 융합 최대오차 |
|---|---|---|
| 2.0 (코스를 살리려 낮춤) | **-20% / -12%** | -116% / -105% |
| 6.0 (게이트를 살리려 올림) | +12% / +3% | (코스 낡음 → -140~-206%) |

**양쪽을 동시에 만족하는 값이 없다.** 그래서 게이트를 살리는 쪽(6.0)으로 두고 융합을
끈다. **코드는 남겨 둔다** — 방향의 출처가 좋아지면 그대로 살아난다.

### 남은 일 — 융합을 살리려면 방향의 출처를 바꿔야 한다

1. **driving 의 확정 헤딩을 받는다**(작업량 작음). driving 은 출발 직진 구간에서

   좋은 값을 들고 있다. ⚠️ 그 헤딩은 *이 노드가 준 위치*로 만들어지므로 **순환**이다.
   끊는 법: **DEGRADED 진입 직전(Fixed 구간) 값만** 받고 그 뒤는 자이로만 얹는다.

일찍 물고 목표보다 위에서 끝난다 = **재가속 없는 안전한 방향**이다.

### ★부수 발견 — A보드 재가속 함정 (`kasa_0804_A.ino`)★

"브레이크 해제 후 재가속이 안 된 원인"을 추적하다 찾았다. **ROS 경로는 결백하다** —
`arduino.py on_tx_timer` 는 A 페이로드가 `'0'→'4'` 로 **바뀌면 즉시** 쓴다(keepalive 대기
없음). 문제는 펌웨어의 적분 안티와인드업 경계다:

```c
const int I_ACCUM_ERR_MAX = 4;
if (pwm > 0 && pwm < PWM_MAX && abs(err) < I_ACCUM_ERR_MAX) pidI[idx] += err;
```

정지한 차(`speed=0`)에 목표를 주면:

| 목표 | err | 적분 | PWM | PWM_MAX(170) 대비 |
|---|---|---|---|---|
| 1펄스 | 1 | 누적 O | 60 → 100 (26.7s) | 59% |
| 2펄스 | 2 | 누적 O | 71 → 111 (13.3s) | 65% |
| 3펄스 | 3 | 누적 O | 81 → 121 (8.9s) | 71% |
| **4펄스** | **4** | **★동결★** | **92 → 영원히 92** | **54%** |

`abs(err) < 4` 이므로 err 가 **정확히 4** 면 거짓 → **적분이 자라지 않는다.**
**목표 4펄스가 목표 2펄스보다 PWM 이 낮다.** LAUNCH 구간에서도 `launchPwm()` 이
`ffPwm`(=90)에 캡을 씌운다. → **BRAKING.md 부록 A 의 "4펄스 12.4초 / 엔코더 0 /
GPS 0.03m" 가 그대로 설명된다.** 기존 가설(B보드 0단 복귀가 위치 미확인 고정 1000ms →
페달이 덜 빠짐)과 **모순이 아니라 곱해진다** — 페달이 걸려 breakaway 힘이 커진 상태에서
펌웨어가 낼 수 있는 토크가 54% 에 묶여 있었다.

**→ 그래서 이 기능은 '절대 세우지 않는' 것을 설계 제약으로 삼는다.** 목표를 2펄스 이상
유지하고 일찍 풀면 해제 시점 속도가 1.8 m/s 근처라 A보드가 보는 `useSpeed` 가 2 로
`LAUNCH_ENTRY_SPEED_MAX(1)` 을 넘어 **기동 블랭킹에 아예 들어가지 않는다** = 허수
카운트도, 재가속 함정도 없다. **펌웨어를 고치지 않고 우회한다**(아래 '하지 않은 것').

### 무엇을 바꿨나 — `corner_brake()` 신설

**구조는 종점 접근제동과 같다 — 되먹임을 만들지 않는다.** 파일 헤더의 세 번의 실패는
*실측 되먹임*('현재펄스 > 목표+3 이면 2단')이 원인이었고, 그 정책은 목표를 0 으로 덮어
LAUNCH 를 재유발하고 그때 쏟아지는 엔코더 허수를 '과속'으로 읽어 또 물었다. 셋 다 피한다:

| | 이 로직 |
|---|---|
| 체결 판정 | **경로 기하만** (남은 거리 + 코너 목표속도). 실측은 안 본다 |
| 해제 판정 | 실측속도(**GPS 전용**). 실측은 **푸는 방향으로만** 작용한다 |
| 목표펄스 | **0 으로 덮지 않는다** (arduino 가 어차피 덮는다 → 해제 시 전이 1회) |
| 재체결 | **코너당 1회.** 해제 후 잠금(시간 + '새 코너' **둘 다**) |
| 속도 출처 | **GPS 만.** `gps_ms()` 가 None 이면 아예 체결하지 않는다 |

`measured_kmh()` 를 쓰지 않는 이유: GPS 가 없으면 `/speed`(**지속 감속을 자세로 오인해
스스로 지운다** — 제동 중이 정확히 그 상황) → 엔코더(**제동 중 REF=0 이라 기동 블랭킹
허수가 섞인다** — 3차 실패에서 자기가 만든 노이즈와 싸운 그 신호)로 내려간다.

**2단은 주행 중 쓰지 않는다**(사용자 결정). 코너는 1단 전용. 부수 효과로 **부록 A 의
'페달이 덜 빠진 채 멈춤' 위험도 함께 줄어든다** — 0단 복귀는 위치를 안 보고 고정 1000ms
REV 인데, 2단은 540카운트(850→310)라 marginal 하지만 **1단은 290카운트라 1.9배 여유**다.

**해제는 예측 선행 — 세 구간의 감속도가 다르다:**

| 구간 | 시간 | 감속도 | Δv |
|---|---|---|---|
| GPS 속도창(0.4s 창 중심) + arduino TX | 0.25 s | 0.88 (제동 100%) | 0.22 |
| 리니어 후퇴(290카운트 ≈ 0.54s, 제동력 a1→a0 감소) | 0.54 s | ≈0.65 | 0.35 |

1. **해제 직후 REF 가 속도를 되돌린다** — `BRAKE_GATE_DECEL(2.0)` 이 낙관값이라 코너

   되올라가** 진입이 2.93펄스였다(목표 2). → **제동을 결정한 코너에 대해 REF 상한을
   `v_corner` 로 둔다**(`_cb_cap`, 낮추는 방향만). 이것은 게이트를 실제 감속도로 계산했을
   때 나올 값과 같으므로 새 정책이 아니라 **낙관값 보정**이다.
2. **완만한 코너(4→3펄스)에서 0.20초만 물렸다** — 리니어는 1단까지 290카운트(≈0.54s)를
   움직여야 하므로 0.2초면 행정의 40% 도 못 가서 **제동력이 거의 안 나오는데 기구는
   왕복한다**(arduino 가 막고 있는 바로 그 동작). → **최소 물림 0.5s** 를 넣고, 체결
   문턱을 그것에서 **파생**시켰다: `해제선행(0.71) + a1(0.88)×최소물림(0.5) = 1.15 m/s`.
   두 가지를 동시에 보장한다 — ⓐ 물면 행정을 끝까지 낸다 ⓑ **목표 밑으로 안 내려간다:
   보장 한계는 `a1 ≤ 문턱/최소물림 = 1.15/0.5 = 2.30 m/s²`** 이고 실측 1단은 0.62~1.05
   다(2단이 2.2~3.8) — 1단이 2.3 에 닿는 것은 행정(raw 600 vs 850)상 성립하지 않는다.
   게다가 행정 램프가 여유를 더 준다(첫 0.5초의 실제 감속량은 `a1×0.5` 의 23% 수준).
   따로 정하면 이 보장이 조용히 깨지므로 파생으로 묶었다.

## 2026-08-18 — GPS 후처리 노드 `gps.py` 신설 : RTK 품질 판정 + IMU 공백 메움

**⚠️ 이 항목은 실차 로그가 아니라 코드·드라이버 소스 분석에서 나왔다.** 아래 ①은
설치된 드라이버 소스를 직접 읽어 확인한 사실이고, ②는 산수다. **실차 검증은 아직
하지 않았다** — 무엇을 어떻게 재야 하는지는 맨 아래에 적었다.

### 무엇이 문제였나

**① `status.status >= 2` 는 "RTK Fixed" 가 아니었다 — "Float 이상" 이었다**

`/fix` 를 만드는 `nmea_navsat_driver` 의 소스
(`/opt/ros/humble/.../libnmea_navsat_driver/driver.py`)를 열어 보면 GGA quality →
`NavSatStatus` 매핑이 이렇다:

| GGA q | 뜻 | status.status | 기본 EPE |
|---|---|---|---|
| 1 | SPS | `STATUS_FIX` (0) | 4.0 m |
| 2 | DGPS | `STATUS_SBAS_FIX` (1) | 0.1 m |
| 4 | **RTK Fixed** | `STATUS_GBAS_FIX` (**2**) | **0.02 m** |
| 5 | **RTK Float** | `STATUS_GBAS_FIX` (**2**) | **4.0 m** |
| 9 | WAAS | `STATUS_GBAS_FIX` (**2**) | 3.0 m |

즉 종전 `driving.py` 의 `RTK_FIXED_STATUS = 2` 판정은 이름과 달리 **오차 수 m 짜리
Float 을 2cm 짜리 Fixed 와 똑같이 통과시키고 있었고, 그 차이가 로그에도 전혀
남지 않았다.** 「2026-08-12 (6)」이 "RTK Fixed 100%" 라고 적은 것도 실은
**"Float 이상 100%"** 였다 — 그 주행이 정말 2cm 좌표였는지는 지금 되짚을 수 없다.

**구별할 값은 같은 메시지 안에 이미 있었다.** 같은 드라이버가
`position_covariance[0] = (HDOP × lon_std_dev)²`, `[4]` 는 위도 쪽을 채운다.
σ = √cov 로 환산하면 Fixed 는 최악(HDOP 5)에도 0.10 m, Float 은 최선(HDOP 0.5)에도
2.00 m 다. **그 사이가 비어 있어서 문턱 하나로 갈린다.**

**② 5Hz fix 사이 3틱이 같은 좌표를 재사용하고 있었다**

제어는 20Hz(0.05초)인데 fix 는 5Hz(0.2초)다. 그 사이 3틱은 좌표가 갱신되지 않으므로
**4.42 m/s 에서 마지막 틱의 좌표는 최대 0.88 m 낡아 있다.** 순수추종은 그 좌표로
목표점 방위(alpha)와 CTE 를 계산한다.

**③ NO FIX 해(解)로도 추종이 계속됐다 (부수적으로 발견)**

종전 `cb_fix` 는 `status` 를 위치 수용에 쓰지 않고 `fix_ok` 플래그에만 썼다. 그래서
`STATUS_NO_FIX` 가 와도 `self.x/self.y` 를 갱신하고 **`fix_time` 까지 리셋했다** →
두절로도 안 잡히고 좌표는 쓰레기인 채 추종이 계속되는 구간이 원리적으로 가능했다.

### 무엇을 바꿨나

**`white1/gps.py` 신설.** `/fix` + `/imu` → `/gps_fused`(20Hz) + `/gps_quality`.
`driving.py` 는 이제 `/fix` 를 직접 구독하지 않는다.

**★상시 보정이 아니다★** 구 `white/gps_imu.py` 는 상보필터로 계속 융합했지만(α
블렌딩·DR 폴백·안테나 투영·GPS 코스 위상정렬) 여기서는 하지 않는다. 규칙은 하나다 —
**원시 fix 가 오면 그 값으로 그냥 스냅한다(블렌딩 없이 덮어쓴다).** IMU 는 fix 가
아직 안 온 시간만 메운다. 그래서 나가는 좌표는 언제나 `최근 원시 fix + 그 뒤 경과
시간만큼의 추측항법` 이고, 두 성분이 `is_raw`·`dr_dist_m` 로 **분리되어** 나간다.

**① 품질 판정** — σ 를 1차 기준, `status.status` 를 상한 게이트로 쓴다.

```
Q_NONE(0) / Q_SPS(1) / Q_DGPS(2) / Q_FLOAT(3) / Q_FIXED(4)
status>=2 이고 σ ≤ RTK_FIXED_SIGMA_M(0.30m)  →  Q_FIXED, 아니면 Q_FLOAT
```

- **왜 q4 를 알아내는 게 아니라 σ 를 보는가** : 수신기가 `$GST` 를 내면 드라이버가
  위 고정 표 대신 **수신기 실시간 오차추정**을 covariance 에 넣는다. 우리가 알고
  싶은 것은 'GGA 숫자'가 아니라 **'이 좌표를 몇 cm 로 믿나'** 이므로 σ 가 질문에 더
  정확히 답한다.
- **covariance 가 비어 있으면 Fixed 로 올리지 않는다.** σ=0 을 '아주 정확'으로 읽으면
  최악의 입력을 최선으로 오해한다 — 모르면 낮게 본다.

**② 공백 메움(DR)** — `ψ = (마지막 GPS 코스) + ∫자이로 dt`, `v = 마지막 GPS 변위
속도`, `가상좌표 = 마지막 fix + ∫v·[cosψ,sinψ]dt`.

- **절대 헤딩을 driving 에서 받아오지 않는다.** 그러면 driving(헤딩)→gps(위치)→
  driving 순환이 생긴다. GPS 코스를 절대 기준으로 삼고 그 뒤 회전만 자이로로 얹어
  이 노드 혼자 닫는다.
- **속도에 엔코더를 쓰지 않는다.** A보드 기동 블랭킹 허수 카운트(「(6)」에서 실측
  최대 77카운트) 로 외삽하면 서 있는 차가 가상좌표상 기어간다.
- **한도 3개** : `DR_MAX_S`(1.0s) / `DR_MAX_DIST_M`(3.0m) / IMU 신선도(0.3s).
  넘으면 **메우지 않는다** — 틀리게 메우면 오차의 크기도 방향도 알 수 없게 되는데,
  안 메우면 오차 상한이 `v·Δt` 로 뻔하다.

**③ 두절 감지를 살려 두기 위한 두 장치** ← **이 변경에서 가장 조심한 부분이다**

DR 로 20Hz 를 계속 내보내면 `driving` 의 `now − fix_time > GPS_TIMEOUT_S(2.0s)`
타이머가 **영원히 리셋되어 두절을 못 잡는다.** 그래서:

- `gps.py` 는 DR 한도를 넘으면 **발행을 멈춘다**(조용히).
- 배열에 `raw_age_s` 를 실어 보내고 `driving` 이 `fix_time = now − raw_age_s` 로
  역산한다 → **DR 로 메운 시간이 두절 판정을 늦추지 않는다.**

**④ Q_NONE 은 발행하지 않는다** (위 문제 ③ 수정) → driving 이 2초 뒤 두절로 판단해
선다. **종전 동작을 의도적으로 바꾼 것이다.**

**② DR 이 실제로 오차를 줄이는가** — `_advance_dr` 수식을 그대로 옮겨 최악 조건

  중이라 추종을 하지 않는다.
- ⚠️ fix 를 절반 유실(2.5Hz)시키면 최대 1.541 m 로 벌어진다. `DR_MAX_S`(1.0s)가

반경 0.9m 창을 0.71m 간격으로 지나가니 **판정이 운에 달렸고**(통과 판정이 그래서

### 무엇을 바꿨나 — 세 단계

### 오작동을 막는 두 가지

## 2026-08-12 (4) — 기록 파일명에 경로 이름, GUI 메인화면(prompt_g), 런치 인자 누락 수정

세 가지를 함께 넣었다. 앞의 둘은 **로그를 나중에 읽는 사람**과 **차 옆에 서서 조작하는

### 1. 주행 기록 CSV — 어느 경로로 달렸는지가 파일명에 없었다

#### 무엇이 관측됐나

8/11 하루에 `gps_data/` 에 경로 4개, `ros2bag/` 에 기록 7개가 쌓였다. 그런데 기록
파일명은 `rec_20260811_214350.csv` 처럼 **시각만** 담고 있어서, 파일 목록만 보고는
그 주행이 `route_20260811_160932` 을 따라간 것인지 `route_20260811_205252` 를
따라간 것인지 알 수 없다. CSV 를 열어 `/drive_cmd` 열을 ffill 해야 비로소 나온다 —
로그를 고르는 단계에서 매번 파일을 열어야 한다는 뜻이다.

#### 무엇을 바꿨나

```
종전 : ros2bag/rec_<날짜>_<시각>.csv
신   : ros2bag/<경로 CSV 이름>-<날짜>_<시각>.csv

  gps_data/route_20260811_160932.csv 로 주행
    → ros2bag/route_20260811_160932-20260812_134501.csv
```

뒤쪽 시각은 종전과 같은 **기록 시작 시각**이다. 같은 초에 두 번 시작하면 `_2` 가 붙는
규칙도 그대로다.

#### 경로 이름을 어떻게 아는가 — 두 곳에서 줍는다

| 출처 | 언제 오는가 | 역할 |
|---|---|---|
| `/drive_cmd` | prompt 가 경로를 고르는 순간 파일명 그대로 | **주 경로** |
| `/drive_event` | driving 의 `📁 경로 선택` · `▶ 주행 시작` | 보조 |

`record` 는 두 토픽을 **이미 구독하고 있었다**(표에 있는 열이다) — 새 구독을 늘리지
않고 지나가는 값을 붙들기만 한다. 보조 경로가 필요한 이유는 record 를 주행 도중에
새로 띄우면 `/drive_cmd` 를 이미 놓친 뒤이기 때문이고, 이때 `▶ 주행 시작(prompt)
[route_….csv]` 이벤트가 **`/drive_state` 보다 먼저** 나가므로(driving 의 `enter()`
안에서 `event()` 가 상태 발행보다 앞선다) 세션이 열리는 시점에는 이름이 도착해 있다.

- `STOP`·`MAP_START`·`DRIVE_START` 는 명령이지 파일명이 아니므로 거른다.
- 이벤트는 '경로 선택'·'주행 시작' 이 들어간 문장에서만 줍는다 — `❌ 경로 파일 없음:
  …/route_bad.csv` 같은 **실패 통보에서 이름을 주워 오지 않기 위해서**다.
- 끝내 못 들으면 `unknown-<시각>.csv` 로 적고 경고를 남긴다. **기록 자체는 거르지
  않는다** — 이름이 없다고 주행 데이터를 버리는 것이 훨씬 손해다.

기존 `rec_*.csv` 들은 건드리지 않는다.

### 2. `prompt_g.py` — prompt 와 같은 기능의 tkinter GUI

#### 왜

차 옆에서 조작할 때 CLI 는 키 입력과 화면 갱신이 섞여 읽기 어렵다. **기능은 그대로
두고 조작면만** 창으로 옮겼다. `prompt.py` 는 남는다(DISPLAY 없는 ssh 에서는 그쪽뿐).

```
 상태 IDLE  |  수동조종
 ┌ /speed  (IMU 환산)      ┐        [ 매 핑 ]
 ┌ /encoder (펄스 × 3.18)  ┐        [ 주 행 ]

 ┌ 조향각 명령 (−좌 / +우) ┐
 ┌ 주행펄스 명령           ┐        [ 종 료 ]
```

| 버튼 | 하는 일 |
|---|---|
| 매핑 | 수동조종이면 즉시 `MAP_START`, 자율주행이면 내릴 때까지 대기 후 발행. 매핑 중에는 **매핑 중단**(`STOP`) |
| 주행 | 파일 선택 창(`gps_data`)에서 경로를 고르면 이름을 발행 → 자율주행이면 즉시 `DRIVE_START`, 수동조종이면 올릴 때까지 대기. 주행 중에는 **주행 중단** |
| 종료 | **이 창(노드)만** 닫는다. 진행 중이면 정지 명령을 보낼지 먼저 묻는다 |

대기·시작 판정 규칙은 `prompt.py` 와 같다 — 화면이 `/vehicle_mode` 를 스스로 폴링해
목표 위치가 되는 순간 START 를 보내고, 안전 게이트는 `driving.cb_drive_cmd` 가 다시
본다. **둘을 동시에 띄우지 말 것**: 깨지지는 않지만(둘 다 발행자일 뿐) 두 화면이 서로
다른 대기 상태를 들고 있게 된다.

설계에서 지킨 것 두 가지:

- **값이 2초 넘게 안 들어오면 `—`.** 죽은 노드의 마지막 숫자를 현재값인 양 띄워 두는
  것이 제일 위험하다. IDLE 에서 `/cmd_vel_raw` 가 멎어 `—` 가 되는 것은 정상이다.
- **ROS 콜백은 값 대입만 하고 위젯을 만지지 않는다.** Tk 는 스레드 안전하지 않다 —
  화면 갱신은 메인 스레드의 `after()` 틱 한 곳뿐이다.

`gps_data` 밖의 파일을 고르면 막는다. `driving.select_route()` 는 `data_dir + 파일명`
으로 여니까 다른 폴더 파일은 이름만 넘어가 '경로 파일 없음' 이 된다.

> ⚠️ **`/encoder` 박스의 환산은 driving 과 다르다.** 지시대로 `펄스합 × 3.18` 만
> 했는데, `/encoder` 는 A보드 **좌+우 합**이라 `driving.py` 는 `ENC_SUM_TO_PULSE`
> (=0.5)를 먼저 곱해 바퀴 하나 기준으로 만든 뒤 3.182 를 곱한다. 즉 이 박스는
> driving 기준보다 **약 2배**로 읽힌다. 맞추려면 `prompt_g.py` 의
> `PULSE_TO_KMH` 를 3.18 → 1.59 로 바꾸면 된다. **미결 사항**이다.

### 3. `one_launch.py` — `cte_ki` 선언 누락 (★(2) 의 회귀★)

#### 무엇이 관측됐나

(2) 에서 `driving` 에 `cte_ki` 파라미터를 넘기도록 `parameters=` 에
`LaunchConfiguration('cte_ki')` 를 더했는데, `DeclareLaunchArgument` 를 빼먹었다.

> `DeclareLaunchArgument('x', …)` 를 **같은 커밋에서** 반드시 함께 넣는다.

신 매핑 → 1.78° pot  ┘ (카운트/도로휠도 = 4.25 로 동일)
```

조향이 반응하지 못하는 측방오차도 그대로다: LFD 5.16 m → **0.26 m**.

> ⚠️ **종전 주석의 0.46 m 는 틀린 값이었다.** pot 각도를 그대로 기하식에 넣어
> 링키지비(1.75)만큼 부풀린 결과다. 맞는 값은 0.26 m 이고, 이건 재측정과 무관하게
> 종전에도 0.26 m 였다. **CTE 적분항의 근거는 그대로 유효하다** — 관측된 편향
> +0.13~0.22 m 는 여전히 이 문턱 아래라 순수추종이 반응하지 못한다.

### 남은 것

- **중심 오프셋 +4 카운트**(= pot 1.19°, 도로휠 0.94°). 구 매핑의 0° 와 신 매핑의
  0° 가 그만큼 다르다. 어느 쪽이 진짜 직진인지는 이 값들만으로 알 수 없다(두 C 값
  모두 하드리밋의 산술중점일 뿐 직진 실측이 아니다). **크기가 CTE 적분항의 작동
  범위 안이라 적분이 흡수한다** — 다음 주행에서 `cte_i_term_deg` 가 이 근처
  (0.9° 도로휠)에서 안정되는지 보면 오프셋의 실체를 역으로 알 수 있다.
- ⚠️ **원 실측(126표본)은 구 매핑으로 달린 로스백이다.** 실측을 다시 한 것이 아니라
  환산만 했으므로, 다음 주행에서 코너 추종을 반드시 확인할 것. 여전히 크게 돌면
  `steer_plant_gain` 을 올린다(= 더 꺾는다).

## 2026-08-12 — IMU 속도계 신설 / 저속 펄스 보정 / 제동 중 구동 차단 / 순차 감속 제거

### A. `speed.py` 신설 — IMU 적분 속도계 `/speed` [km/h]

엔코더도 GPS 도 저속에서 못 쓴다는 것이 어제 로그로 드러났다(엔코더는 정지 중
2.5~5펄스의 허수 카운트, GPS 는 5Hz 라 최소 0.2초 지연 + 저속에서 노이즈가 지배).
그래서 20Hz IMU 를 적분하는 노드를 만들었다.

**설계 — 실측으로 정한 것**

1. **축 하나를 그냥 적분하면 안 된다.** 정지 시 가속도 평균이
   `(−5.21, −1.05, +8.25) m/s²`, 크기 정확히 9.81 — 가속도계는 중력을 포함하고
   센서가 32° 기울어 장착돼 있다. 축별 단독 적분은 26초에 `x −1.86 / y +1.83 /
   z −1.10 m/s` 로 **부호조차 안 맞는다**(실제 +3.5).
2. **쿼터니언으로 월드 변환하면 맞는다.** 정지 시 월드 가속도가
   `(0.068, 0.027, 9.810)` 으로 중력이 Z 에 정확히 정렬된다.
3. **ZUPT(영속도 보정)로 드리프트를 잡는다.** 순수 IMU 는 '정지'와 '등속'을
   원리적으로 구별 못 하지만, 이 차에서는 노면 진동이 구별해 준다 —
   `|a|` 의 0.5초 이동 표준편차가 완전정지 0.064 / 0.05~0.3 m/s 0.279 /
   주행 0.58~1.14 로 **15배 벌어진다**. 임계 0.15 면 기어가는 것을 정지로
   오판하지 않는다.

**★한계 — 반드시 알고 쓸 것★**

로그를 이 알고리즘에 그대로 흘려 GPS 와 대조했다:

| 시각 | speed.py | GPS 실측 |
|---|---|---|
| t=40 | 0.75 | 1.18 km/h |
| t=50 | 1.68 | 4.16 |
| t=56 | 3.11 | 8.71 |
| t=62 | 8.13 | **17.37** |

절반 수준으로 과소평가한다. 원인은 적분이 아니라 **AHRS 자세가 지속 가속에
오염되는 것** — 피치가 정지 32.49° → 주행 30.10° 로 2.4° 흔들렸고, 중력 누출
0.41 m/s² 는 이 주행의 평균 가속도 0.185 m/s² 보다 크다. 자세가 우리가 재려는
신호를 스스로 지운다.

자세를 자이로로만 전파해도(스트랩다운) 나아지지 않는다 — 이번엔 반대로
**1.6배 과대평가**(t=62 에서 26.83 / 17.37). 자이로 드리프트가 반대 방향으로
중력을 새게 한다.

**결론**: 이 하드웨어에서 순수 IMU 적분의 절대속도는 26초 창에서 2배 수준으로
틀린다. 대신 **'서 있는가 움직이는가'는 아주 정확하다** — 그리고 그것이 엔코더가
못 하는 일이다. 아래 B 의 보정량을 ±2펄스로 묶고 REF 3 이하로 제한한 이유가 이것.

### B. 저속 펄스 보정 — `driving.py`

지령 1펄스를 30.8초 줬는데 10초를 아예 서 있었던 구간(어제 E 항)에 대한 대응.
저속에서는 인휠 토크와 타이어 스크럽 부하가 맞물려 지령과 실제 속도의 관계가
무너지므로, **낮은 REF 에서만** 실제 속도를 보고 REF 를 밀어 준다.

```
out = REF + clamp(REF − 실측펄스, −2, +2),   0 ≤ out ≤ 15
```

동작 조건을 좁게 잡았다:

- **`DRIVE_RUN` 이고 `1 ≤ REF ≤ 3` 일 때만.**
  REF 0 에서는 절대 걸지 않는다(세우려는 지시를 보정이 뒤집으면 안 된다).
  REF 4 이상에서 걸면 `MAX_PULSE_LIMIT`(4)를 우회하는 과속 경로가 된다.
  `DRIVE_HEADING` 은 곧게 굴러 헤딩을 잡는 구간이라 속도를 흔들면 안 된다.
- **실측은 `/speed` 우선, 없거나 0.5초 넘게 오래됐으면 엔코더로 내려간다.**
- **0.3초 주기로만 다시 판단한다**(REF 가 바뀌면 즉시). 20Hz 로 매 틱 계산하면
  속도가 따라오기 전에 보정이 널뛴다.

동작 확인:

| REF | 실측 | 발행 |
|---|---|---|
| 3 | 1펄스 | **5펄스** ← 지시하신 예시 |
| 3 | 2펄스 | 4펄스 |
| 3 | 3펄스 | **3펄스** ← 속도 도달, 보정 해제 |
| 3 | 5.5펄스 | 1펄스 |
| 4 | 1펄스 | 4펄스 (미동작) |
| 0 | 0펄스 | 0펄스 (미동작) |

`MAX_PULSE_LIMIT`(4)와의 관계: 그 상한은 **기준속도(REF)의 천장**이고 보정은
**기동을 위한 일시적 가산**이라 성격이 다르다. 그래서 자르는 순서가 REF → 보정
→ 0~15 이고, 실제 상한은 3+2 = **5펄스**다.

검증 가능하도록 `/drive_diag` 에 `ref_pulse` · `out_pulse` · `meas_pulse` 3열을
추가했다(record 도 함께 갱신). **`out ≠ ref` 인 구간이 보정이 걸린 구간**이다.

### C. 제동 중 구동 차단 — `nxde/arduino.py`

### D. 순차 감속 제거 — 어제 넣은 종점 선행제동을 걷어냈다

어제 넣은 `GOAL_BRAKE_DECEL`/`GOAL_BRAKE_MARGIN_M`(종점 4→3→2펄스 순차 감속)을
**제거**했다. 정지는 리니어 2단이 담당하고(실측 감속도 2.2 m/s²), 속도를 미리
깎는 것은 그 일을 대신하지 못하면서 종점 구간만 길게 만든다.

**지금 정책**: 종점까지 곡률이 허락하는 속도로 가고, 도착 또는 코스 이탈 판정이
서는 순간 `DRIVE_DONE` 으로 넘어가 **조향 0(일직선) + 리니어 2단**으로 세운다.
완전정지(엔코더 0)가 2초 유지되면 리니어 0단 + IDLE.

⚠️ **그래서 도착 판정이 유일한 방벽이 됐다.** 접근속도가 다시 4펄스대로 올라가므로
반경(0.9 m)만으로는 5Hz GPS 에서 놓칠 수 있고, **통과 판정**(마지막 WP 가 차체 뒤로
넘어감)이 반드시 함께 있어야 한다 — 어제 넣은 그 조건이 이제 주 판정이다.
리니어 체결 시점 속도가 3.5~4.8 m/s 이므로 **정지 위치는 종점에서 약 2 m 뒤**가
된다(어제 실측 정지거리).

### A. 종점을 4펄스로 질주했다

**관측** (GPS 변위 기준 실제 속도, 214852)

| 종점까지 남은 거리 | 실제 속도 |
|---|---|
| 3.25 m | 4.58 m/s |
| 1.14 m | **4.83 m/s = 17.4 km/h** |
| 0.40 m | 3.74 m/s |

**원인 1 — 종점 감속 항이 코드에 아예 없었다.**
`corner_speed()` 는 곡률만 보고 속도를 정했고 `d2goal` 인자조차 없었다.
`lookahead_m()` 의 종점 캡은 **LFD 만** 줄이고 속도는 건드리지 않는다.
경로 곡률을 오프라인 재계산해 보면 마지막 8 m 는 전부 4펄스 지령 구간이었고,
실제 로그에서도 t=60.1(종점 7.13 m 전)에 4펄스로 올라가 그대로 종점에 꽂았다.

**원인 2 — 지령보다 실제가 더 빠르다.**
4펄스 지령(3.54 m/s)인데 GPS 실측 4.83 m/s. 개루프 펄스 지령이라 실제 속도가
지령을 1.36배 넘겼다.

**수정**

- `driving.py` 에 **종점 선행제동** 추가 — 코너 게이팅과 같은 식, 감속도만 완만하게.
  ```
  v_goal = √(2 · GOAL_BRAKE_DECEL · (남은거리 − GOAL_BRAKE_MARGIN_M))
  GOAL_BRAKE_DECEL    = 1.5 m/s²
  GOAL_BRAKE_MARGIN_M = 1.0 m
  ```
  `corner_speed()` 가 `d2goal` 을 인자로 받고 (c) 항에서 이 값으로 목표속도를 누른다.
  하한은 기존 `CORNER_MIN_PULSE`(2) 를 그대로 쓴다.

  실제 경로에 적용한 결과:

  | 종점까지 | 지령 |
  |---|---|
  | 4.3 m | 4펄스 |
  | 4.0 m | 3펄스 |
  | 2.4 m | 2펄스 |
  | 도착까지 | 2펄스 유지 (1.77 m/s) |

- **최고속도 절대 상한** `MAX_PULSE_LIMIT = 4` 신설.
  `send()` 가 마지막에 무조건 이 값으로 자르고, 파라미터(`drive_pulse`,
  `heading_pulse`)도 읽는 즉시 같은 값으로 자른다.
  ※ `send()` 에서만 자르면 `max_speed_ms`(속도대역·LFD 식의 기준)가 안 잘린 값으로
  남아 계산과 출력이 어긋나므로 두 곳 다 잘라야 한다.
  기존 상한은 프로토콜 상한 15 라 사실상 없는 것과 같았다.

### B. 도착 판정이 원리적으로 성립할 수 없었다

**관측** — 최근접 거리 0.24 m(214350) / 0.38 m(214852). 둘 다 `WP_REACH_M`(0.2 m) 밖.

**원인** — GPS 는 5 Hz(0.20 s)다. 종점 접근속도 4.8 m/s 면 샘플 간 이동거리가
**0.96 m** 라 반경 0.2 m 창을 통째로 건너뛴다. 조건이 반경 하나뿐이었으므로
(`wp_idx == 마지막 and d2goal <= 0.2`) 한 번 놓치면 그대로 질주했다.

**수정** — `run_follow()` 의 종점 판정을 둘로 늘렸다. **둘 중 먼저 되는 쪽이 도착**이다.

1. **반경** : `WP_REACH_M` 0.2 → **0.9 m** (launch `wp_reach_m` 기본값도 함께)
   A 의 종점 감속으로 접근속도가 1.77 m/s 가 되어 샘플 간격이 0.35 m 이므로
   0.9 m 창은 2~3회 샘플된다.
2. **통과** : 마지막 WP 가 차체기준 뒤로 넘어갔으면(전방거리 < 0) 도착.
   반경은 '가까웠던 순간을 샘플했는가'에 의존하지만 통과는 한 번 지나가면 반드시
   성립한다 — 종점 질주의 마지막 방벽이다. 이격 `GOAL_PASS_MAX_M`(2.5 m) 이내에서만
   인정하고, 그보다 멀면 '지나쳤다'가 아니라 '벗어났다'로 보고 CTE 이탈감지에 맡긴다.

두 판정 모두 **남은 호길이 `GOAL_ZONE_M`(6.0 m) 이내에서만** 본다 —
순환 코스에서 출발점 부근을 종점으로 오검출하는 것을 막는다.

### C. 종점에서 조향이 폭주했다

**관측** (214350)

```
종점 1.36 m : 조향지령 +25.2°
종점 0.64 m : 조향지령 +40.0°   ← pot 상한 포화

리니어 2단과 같은 틱에** 내보내도록 바꿨다. 예전에는 다음 `loop()` 틱(최대 50 ms 뒤)
에야 조향 0 이 나갔고, 그 50 ms 동안 B보드가 직전 각을 향해 계속 슬루했다.

### D. 리니어는 정상이었다 — 늦게 물렸을 뿐이다

관찰상 "도착했는데 리니어가 안 걸린다"였지만 로그는 다르게 말한다.

- `/brake_level = 2` 는 정상 발행됐고, `nxde/arduino.py` 의 **(4) 정상 자율주행**
  분기가 그대로 B보드로 넘긴다. 경로에 막히는 곳이 없다.
- 214350 제동 후 감속 : 2.09 → 1.30 → 0.55 → 0.08 m/s (0.6 초), 총 정지거리 약 2 m,
  평균 **2.2 m/s²**. 물리적으로 작동했다.

문제는 **언제** 물렸는가다. 도착 판정(B)이 실패했으므로 리니어를 부른 것은 도착이
아니라 CTE 이탈 감지였고, 그 지점이 이미 종점 2 m 뒤였다. 그래서 밖에서는 안 걸린
것처럼 보였다. **고친 곳은 리니어가 아니라 A·B 다.**

또 하나, 그때의 CTE 는 옆으로 벗어난 거리가 아니다 — 마지막 WP 를 지나면
`signed_cte()` 가 마지막 선분 끝점으로 clamp 되므로 `cte == goal_dist` 가 된다
(로그에서 두 열이 정확히 일치한다). 이탈 감지기가 우연히 '종점 2 m 초과 통과
감지기' 역할을 하고 있었던 셈이다.

**도착 시 동작(확정)**

```
종점 도달 → 조향 0(일직선) + 펄스 0 + 리니어 2단   (같은 틱)
         → 엔코더 0 이 2초 유지되면 리니어 0단 + IDLE(메뉴 복귀)
```

하한이 2펄스이므로 도착 순간 속도는 1.77 m/s 이고, 리니어 2단이 나머지를 맡는다
(관측 감속도 2.2 m/s² → 정지거리 약 0.7 m). **종점을 0.7 m 정도 지나 서는 것은
설계된 동작이다.**

### E. 코너에서 차가 거의 안 굴렀다 — 코드는 이미 고쳐져 있었고, 안 실린 것이다

**관측** (214852)

| 구간 | 지령 | 실제 속도 |
|---|---|---|
| t=26~36 (10 초) | 1펄스 | **0.00 m/s — 완전 정지** |
| t=36~52 (16 초) | 1펄스 | 0.04 → 1.00 m/s |

`cmd_pulse = 1` 이 주행의 **52 %(30.8 초)** 를 차지했고, 그 동안 `wp_idx` 는
65 → 89, 즉 31 초에 6 m 갔다.

**원인 1 — 정수 펄스 반올림이 하한을 30 % 깎는다.**
`min_speed_ms = max(0.9, 3.54/2.8) = 1.26 m/s` → `int(1.26/0.884+0.5) = 1펄스
= 0.884 m/s`.

**원인 2 — 감속 곡선이 이 경로에 대해 너무 가파르다.**
이 경로의 요구 도로휠각은 win 최대 15.4° / peak 최대 17.0° 인데
`STEER_FULL_SLOWDOWN_DEG = 15.0` 이다. 코너 구간(WP 65~90, 약 12 m) 전체가
"최대 감속" 영역에 그대로 걸린다 — 곡률 비례 감속이 아니라 사실상
**코너 진입 = 최저속도 고정**이다.

**원인 3 — `CORNER_MIN_PULSE = 2` 가 이 두 주행에 실리지 않았다.**
현 소스는 하한을 2 로 묶으므로 1펄스가 나올 수 없다. 그런데 로그에는 1펄스가
51~52 % 찍혀 있다 → **노드를 재시작하지 않아 반영되지 않은 채 달렸다**(확인됨).

**수정** — 코드 변경 없음. 하한 2 는 이미 들어가 있다. 상수 주석에
**"아직 실차 검증 전"** 을 명시했다. 원인 2(`STEER_FULL_SLOWDOWN_DEG`)는
하한 2 를 실제로 태워 본 뒤에 판단한다 — 먼저 건드리면 무엇이 효과를 냈는지
구분할 수 없다.
